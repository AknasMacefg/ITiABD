# Лабораторная работа 2: `curl`, SQL JOIN и объединение данных

Проект показывает полный конвейер подготовки данных:

```text
curl и REST API
        ↓
CSV + API + SQLite
        ↓
проверка типов, ключей и кардинальности
        ↓
pandas.merge и SQL JOIN
        ↓
сравнение результатов
        ↓
аналитическая витрина
        ↓
графики и подготовка данных для BI
```

Главный результат работы — понимание того, что получение данных и их
объединение являются разными этапами инженерного процесса.

## 1. Назначение файлов по порядку выполнения

Ниже перечислены все содержательные файлы проекта. Служебные
`__init__.py` и автоматически создаваемые каталоги `__pycache__` в список
не включены.

### 1.1. `requirements.txt`

Файл зависимостей проекта. В нём зафиксированы библиотеки, необходимые для
запуска лабораторной:

- `fastapi` — учебный REST API;
- `uvicorn` — локальный ASGI-сервер;
- `pandas` — загрузка, очистка и объединение таблиц;
- `requests` — программный HTTP-запрос к API;
- `matplotlib` — построение графиков;
- `pyarrow` — сохранение витрины в Parquet.

Установка выполняется из каталога `lab_2`:

```powershell
python -m pip install -r requirements.txt
```

### 1.2. `app/main.py`

Учебное FastAPI-приложение, имитирующее REST-источник транзакций
`GET /api/transactions`. Файл:

- читает начальные операции из `data/transactions_api.json`;
- реализует GET списка и одной операции;
- фильтрует список по `org_id` и `currency`;
- принимает POST для создания операции;
- принимает PUT для полной замены операции;
- принимает PATCH для частичного изменения;
- принимает DELETE;
- реализует HEAD;
- предоставляет `/api/redirect` для проверки `curl -L`;
- проверяет входные данные через модели Pydantic.

Сервер запускается так:

```powershell
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

### 1.3. `data/organizations.csv`

Первый источник данных — CSV со справочником организаций. Его назначение —
хранить сторону «одна» в связи с транзакциями:

| Поле | Назначение |
|---|---|
| `org_id` | уникальный идентификатор организации и ключ связи с API |
| `org_name` | название организации |
| `city_id` | ключ связи со справочником городов |
| `sector` | отрасль организации |

В текущем наборе есть организации, которым можно сопоставить операции, и
организация `org_id=10` без операции. Это позволяет увидеть разницу между
INNER JOIN и LEFT JOIN непосредственно в ноутбуке.

### 1.4. `data/transactions_api.json`

Локальное начальное состояние REST API. Это не отдельная таблица,
загружаемая напрямую в ноутбуке: `app/main.py` читает этот JSON и отдаёт его
через HTTP. В записях находятся:

- `transaction_id` — идентификатор операции;
- `org_id` — внешний ключ организации;
- `date` — дата;
- `amount` — сумма;
- `currency` — валюта.

В файл намеренно включены проблемные данные: неизвестный `org_id=999` и
повторяющаяся строка. Поэтому API показывает, что качество источника нужно
проверять до JOIN.

### 1.5. `data/regions.db`

SQLite-база второго справочного источника. В таблице `cities` хранятся:

| Поле | Назначение |
|---|---|
| `city_id` | ключ города и связь с `organizations.city_id` |
| `city_name` | название города |
| `region_name` | регион |
| `population` | население |

Связь `organizations.city_id -> cities.city_id` ожидается как `N:1`:
несколько организаций могут находиться в одном городе, а справочник городов
должен содержать один ряд на `city_id`. Наличие города без организации
проверяется как ключ, присутствующий только справа.

### 1.6. `src/loaders.py`

Модуль загрузки трёх источников в `pandas.DataFrame`:

- `load_organizations()` читает `organizations.csv`;
- `load_transactions()` выполняет `requests.get()` к REST API, проверяет
  HTTP-ошибки через `raise_for_status()` и преобразует JSON в DataFrame;
- `load_cities()` выполняет SQL-запрос к SQLite и получает таблицу `cities`;
- `load_sources()` запускает все три загрузчика и возвращает словарь
  `organizations`, `transactions`, `cities`.

Таким образом, модуль отделяет получение данных от последующей обработки.

### 1.7. `src/transform.py`

Модуль преобразования и объединения данных средствами pandas:

- `normalize_keys()` приводит `org_id` и `city_id` к совместимому типу
  `Int64`;
- `key_diagnostics()` проверяет NULL, повторяющиеся ключи, ключи только
  слева и ключи только справа;
- `join_sources()` выполняет:
  1. `organizations INNER JOIN transactions`;
  2. `organizations LEFT JOIN transactions`;
  3. `LEFT JOIN cities`;
- `indicator=True` сохраняет происхождение строк в `_merge` или
  `city_merge`;
- `validate="one_to_many"` проверяет связь организации с операциями;
- `validate="many_to_one"` проверяет связь организаций с городами;
- `build_data_mart()` группирует объединённые данные и рассчитывает
  количество операций, сумму, среднее и дату последней операции.

Ожидаемые кардинальности:

- `organizations.org_id -> transactions.org_id`: `1:N`;
- `organizations.city_id -> cities.city_id`: `N:1`;
- `transaction_id` должен быть уникальным, поэтому повтор операции является
  проблемой качества данных, а не новой корректной операцией.

### 1.8. `src/database.py`

Модуль повторяет контрольные объединения в SQLite:

- `create_database()` загружает подготовленные DataFrame во временные
  таблицы `organizations`, `transactions` и `cities`;
- `run_joins()` выполняет SQL `INNER JOIN` и два `LEFT JOIN`;
- `aggregate_transactions()` выполняет `GROUP BY` и использует
  `COUNT(...)`, `SUM(...)`, `AVG(...)` и `COALESCE(...)`.

Этот модуль нужен для сравнения двух реализаций одного правила объединения:
`pandas.merge()` и SQL JOIN.

## 3. Почему результаты INNER JOIN и LEFT JOIN различаются

`INNER JOIN` оставляет только строки, для которых ключ найден в обеих
таблицах. Поэтому операция с неизвестным `org_id=999` исчезает, как и
организация без операции.

`LEFT JOIN` сохраняет все строки левой таблицы. Поэтому при
`organizations LEFT JOIN transactions` организация без операции остаётся,
а поля транзакции имеют `NULL`. При последующем `LEFT JOIN cities`
сохраняются и организации с отсутствующим городом; поля города также
становятся `NULL`.

Статистику нужно читать по `indicator`:

- `both` — соответствие найдено;
- `left_only` — ключ есть только слева;
- `right_only` — ключ есть только справа.

## 4. Ответы на вопросы к защите

### Что такое INNER JOIN?

`INNER JOIN` объединяет строки по условию `ON` и возвращает только
совпавшие ключи. Несопоставленные строки обеих таблиц отбрасываются.

### Что такое LEFT JOIN?

`LEFT JOIN` возвращает все строки левой таблицы и совпавшие строки правой.
Если соответствия справа нет, правые столбцы заполняются `NULL`. Это
правильный выбор, когда нельзя потерять организации без операций.

### Что означает связь 1:N?

`1:N` означает, что одной строке первой таблицы соответствует много строк
второй. В работе одна организация может иметь много транзакций. При таком
JOIN строка организации повторяется для каждой её операции, что ожидаемо.
Именно поэтому используется `validate="one_to_many"`.

### Что такое ключ и зачем он нужен?

Ключ — столбец или набор столбцов, однозначно идентифицирующий сущность и
позволяющий найти соответствующую строку в другой таблице. `org_id`
связывает организации и транзакции, а `city_id` — организации и города.
Ключи должны иметь совместимые типы; дубликаты и NULL нарушают ожидаемую
кардинальность и требуют отдельной диагностики.

### Почему после JOIN возникают дубликаты?

Если ключ повторяется справа, одна строка слева соединяется с каждой
подходящей строкой справа. При `1:N` это не ошибка: повторяется организация,
но меняется операция. Если повторяется сам `transaction_id`, как в
намеренно испорченном источнике, сумма и количество операций могут быть
завышены. Поэтому нужно проверять дубли до JOIN и не удалять их молча.

### Почему нельзя сразу вызвать `merge()`?

Без проверки типов, NULL, дублей и кардинальности нельзя понять, является ли
получившийся размер результата корректным. Сначала определяются ожидаемые
отношения `1:N` и `N:1`, затем `indicator=True` показывает происхождение
строк, а `validate` останавливает объединение при нарушении схемы связи.

### Совпадают ли SQL JOIN и `pandas.merge()`?

При одинаковых исходных таблицах, ключах и условиях `ON` они должны дать
одинаковое число строк и одинаковые агрегаты. Различия появляются, если
одна реализация дополнительно удаляет дубли, фильтрует строки, по-разному
обрабатывает NULL или агрегирует до JOIN. В этой работе SQL используется как
независимая проверка результата pandas.

### Чем curl отличается от библиотеки Requests?

`curl` — командная утилита, удобная для ручной диагностики HTTP, проверки
заголовков, redirect, разных протоколов и быстрого сохранения ответа.
`requests` — Python-библиотека для программного доступа к HTTP: её удобно
встраивать в функции, обрабатывать JSON, проверять ошибки и передавать
результат дальше в pandas. `curl` подходит для воспроизводимой команды
терминала, а `requests` — для автоматизированного ETL-кода.
